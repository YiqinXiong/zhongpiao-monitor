# 中票优品「京东E卡」补货监控与提醒方案

> 目标站点：https://zpmall.zhongpiaofuli.com （中票优品 H5 商城，uni-app 构建）
> 目标商品：【京东E卡】100面值（productId `12325240480631807`，skuId `12325240480893951`，售价 132）
> 账号情况：已绑定 2 张福利卡合计约 1000+ 点数余额；Edge 浏览器已登录（手机验证码登录）
> 可运行环境：一台 Linux 服务器 + 本机 ARM MacBook
> 方案版本：v1.0（2026-10-16，含实测逆向结论与可运行原型 `zpmon/`）

## 0. 结论摘要（TL;DR）

| 问题 | 结论 |
| --- | --- |
| 能否监控补货？ | **能，且监控查库存无需登录**。已实测：商品接口对游客开放 |
| 技术门槛 | 低。接口为统一 JSON API + MD5 签名（算法已逆向并复刻成功） |
| 登录态/验证码 | 登录态 = localStorage 中的 `apiToken`。可从 Edge 一键取出复用；验证码只需人工收一次，无法也不建议全自动 |
| 补货检测 | 轮询 `app_get_h5product_sku_check`（推荐）/ `app_get_h5product_detail`，判定字段 `usableStocks > 0`；商品三态（在架有货/补货中/下架）全覆盖 |
| 提醒渠道 | Bark（iOS 最快）/ Telegram / PushPlus / Server酱 / 钉钉 / 企微 / 飞书 / 自定义 webhook，多路并发 |
| 自动下单 | **技术上可行**（已走通全链路 API），默认 dryRun 不扣款；支持多品种各自配置充值账号；每品种每日限量 1 张，买成功当天自动停止该品种、次日恢复 |
| 主要风险 | 违反平台用户协议可能封号；余额损失；频率过高可能限 IP。详见第 7、8 章 |
| 注意 | 监控与城市无关；商品三态（在架有货/补货中/下架）全覆盖 |

## 1. 站点逆向结论（已实测验证）

### 1.1 技术栈

- **uni-app 编译的 H5**（页面元素为 `uni-view` 自定义标签），Vue 全家桶，webpack 分包加载
- 入口即 SPA，必须执行 JS；但**所有业务数据都走 JSON API**，不需要渲染页面即可监控

### 1.2 API 全景（统一网关）

所有业务请求都是：

```
POST https://zpmall-api.zhongpiaofuli.com/mall/MallApi/handle
Content-Type: application/json

请求头：
  methodName: app_get_h5product_detail   # 方法名
  appKey:      3dfde15355fd0442f81defcbd02a7a10   # 固定
  timeStamp:   1792132898839
  paramSign:   <md5签名>
  apiToken:    <登录令牌，未登录为空>

请求体（JSON）：{...业务参数, "timeStamp": ..., "methodName": "..."}
```

**签名算法**（已复刻验证，与抓包逐位一致）：

```text
p = ""
for k in sorted(参数键):        # 按 key 字典序
    if 值非 null: p += k + "=" + JSON序列化或原值 + "&"
p += "appKey=3dfde15355fd0442f81defcbd02a7a10"
paramSign = md5(p)
```

> 注意：`apiToken` 长度 > 64 时才加入待签名参数（与前端 JS 一致）。

### 1.3 已梳理的接口清单

| 方法名 | 用途 | 需要登录 |
| --- | --- | --- |
| `app_get_h5product_list` | 商品搜索/列表（含 `usableStocks` 库存） | 否 |
| `app_get_h5product_detail` | 商品详情（含 `remindMessageTip` 补货提示、`skuList[].usableStocks`） | 否 |
| `app_get_h5product_sku_check` | 下单前权威库存校验 | 否 |
| `app_get_phone_sms_code_send` | 发送短信验证码（模板 `SMS_199890295`） | 否 |
| `app_set_phone_sms_code_login` | 验证码登录，返回 `apiToken` | 否 |
| `app_get_h5member_ptcard_list` | 我的点数卡列表（cardNo/balanceNum/deducteNum） | **是** |
| `app_set_h5product_shopcart_add` | 立即购买/加购（`commitFrom=1` 为立即购买），返回 `shopCartId` | **是** |
| `app_get_h5order_preview` | 订单预览：点数抵扣拆分、微信补付金额 `orderWxPayAmount` | **是** |
| `app_get_h5order_commit` | 提交订单；`wxPayAmount=0` 时无需微信支付即下单成功 | **是** |

### 1.4 库存判定字段（实测当前值）

`app_get_h5product_detail`（productId=12325240480631807）当前返回：

```json
{
  "product": {
    "productName": "【京东E卡】100面值",
    "remindMessageTip": "抱歉，该商品正在补货中！",
    "skuList": [{ "skuId": "12325240480893951", "usableStocks": 0, "salePrice": 132.0 }]
  }
}
```

对照实验：`【京东】plus会员年卡` 的 `usableStocks = 9862`（有货），咪咕阅读等商品该字段为 `null`（不限量/未同步）。
**判定规则：`remindMessageTip` 为空 且 任一 sku `usableStocks > 0` → 有货。**

**商品三态（2026-10-17 实测）**：

| 状态 | 列表接口 | 详情接口 | sku_check |
| --- | --- | --- | --- |
| 在架有货 | 在列，usableStocks>0 | 正常，remind 为空 | usableStocks>0 |
| 在架缺货（补货中） | 在列，usableStocks=0 | remindMessageTip="抱歉，该商品正在补货中！" | usableStocks=0 |
| **下架**（京东E卡当前状态） | 不在列 | code=1000「该商品暂时无法购买」 | 仍可用，usableStocks=0 |

三种状态监控均覆盖（见 5.1 三种模式），下架商品重新上架瞬间即触发提醒。

**库存监控与城市无关（2026-10-19 实测确认）**：同一商品在不同城市查到的库存一致（京东E卡/盒马/中石化/三网通在深圳均可正常监控）。此前一次测试搜不到商品，是因为当时它们恰好都没上架。`cityCode` 仅影响列表/详情的查询上下文，监控目标无需按城市区分。

### 1.5 登录态本质

- uni-app H5 把令牌存在 `localStorage`：键名 `apiToken`（另有 `cityCode`、`cityName`）
- 请求时以 `apiToken` 请求头传递；服务端无 Cookie 会话依赖
- **推论：从 Edge 开发者工具取出 `apiToken`，即可在任何脚本/服务器上复用同一登录态**

## 3. 技术选型

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 语言 | Python 3.10+ | 逆向验证快、requests 生态成熟、服务器免运维运行时 |
| HTTP | requests + Session  keep-alive | 连接复用降低握手延迟（抢购时每 100ms 都值钱） |
| 签名 | 标准库 hashlib | 算法简单，无需第三方库 |
| 调度 | 单进程 while 循环 + 随机抖动 | 目标少（1~2 个），无需 APScheduler/Celery |
| 常驻 | systemd（Linux） | 崩溃自拉起、开机自启、日志进 journald |
| 浏览器自动化（仅登录助手用） | Playwright（chromium） | 一次登录取 token；ARM Mac 与 Linux 均支持 |
| 配置 | JSON 文件 + 环境变量可覆盖 | 简单直观，便于 git 管理（token 除外） |

**为什么不用浏览器方案常驻监控**（Playwright 定时打开页面）：
Chromium 常驻内存 300MB+，且要等 SPA 渲染；纯 API 轮询单次请求约 100~300ms、内存 <50MB，且**未登录就能查库存**， token 过期也不影响监控连续性。

## 4. 登录态与验证码的处理方式

### 4.1 三种获取 `apiToken` 的方式（按推荐排序）

**方式 A：从 Edge 直接取出（零成本，推荐先这样）**

Edge 已登录的前提下：

1. F12 打开开发者工具 → Application → Local Storage → `https://zpmall.zhongpiaofuli.com`
2. 找到键 `apiToken`，复制值（约 100+ 位字符串）填入 `config.json` 的 `apiToken`
   （或在 Console 执行 `localStorage.getItem('apiToken')`）

**方式 B：登录助手半自动（推荐作为长期方案）**

`login_helper.py`（Playwright）自动打开登录页 → 你输入手机号、收取短信验证码、手动登录 →
脚本轮询 localStorage 自动捕获 `apiToken` 并落盘 `token.json`。验证码环节**必须人工**，原因见 4.2。

**方式 C：全 API 登录（不推荐日常用）**

直接调 `app_get_phone_sms_code_send` + `app_set_phone_sms_code_login`。
验证码仍需你从手机短信里读出并输入，只比方式 B 少一个浏览器，但容易触发风控校验，仅作备用。

### 4.2 验证码为什么不能全自动

短信验证码发送到你本人手机号，脚本要"自动收码"只有三条路，均有明显缺陷：

| 方案 | 缺陷 |
| --- | --- |
| 安卓手机 + 短信转发到服务器 | 需要额外养一台安卓机/Tasker，链路长 |
| 第三方接码平台 | 号码非本人实名，**违反平台协议，可能涉嫌违法**，坚决不建议 |
| 运营商和阿里云语音/短信通知 | 只能收不能收"登录验证码"场景，不适用 |

结论：**验证码人工收一次，token 复用很久**（未发现短时效，失效后重新登录即可，监控不受影响）。

### 4.3 Token 治理

- 失效表现：带 token 的接口返回 code≠200 / 提示未登录 → 重新走 4.1 换 token
- 安全：token = 账号完全权限，`token.json` / `config.json` 设 `chmod 600`，**不要提交 git**，不要外发
- 监控与下单解耦：监控不依赖 token；token 失效期间监控照常工作，只是不能自动下单

## 5. 补货状态的检测策略

### 5.1 检测对象与频率

| 模式 | 接口 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **sku 模式（推荐主力）** | `app_get_h5product_sku_check` | 不受上下架/城市上架影响，最轻量稳健；下单前权威校验同一接口 | 信息维度少 |
| detail 模式 | `app_get_h5product_detail` | 判定最权威（remindMessageTip + sku 库存） | 下架时报 code=1000（程序已按无货处理并持续监控） |
| search 模式（辅） | `app_get_h5product_list` | 能发现新增面值/新上架商品 | 仅 usableStocks 一个字段 |

### 5.1.1 限流与每日配额（实测踩坑）

平台对**同一出口 IP** 有每日请求配额，超限返回
`code=1000 msg=IP[x.x.x.x]今日访问频繁`。实测特征：

- **无突发限流**：20 次请求/0.9 秒可全部通过 → 限制是**日配额**而非瞬时 QPS
- **不支持缓存协商**：响应无 ETag/Cache-Control，无法用 304 省配额
- **搜索结果有上限**（约 10 条，按相关度排序），无法用一次搜索覆盖多个品类

早期版本「每 10 秒并发查 5 个目标」= 43,200 次/天，几小时即烧穿配额。当前调度：

1. **分时段 + 串行轮转**：按 `schedule` 时间窗决定节奏（默认 09:00–17:00 每 60s、其余每 180s），
   每轮最多 1 个请求，按各目标间隔轮转
2. **每日预算**：`dailyRequestBudget`（默认 4000）内按计划量等比缩放间隔，永不超预算
3. **限流退避**：触发即暂停 30 分钟 + 间隔 ×2（上限 ×16）+ 推送通知；反复触发暂停到次日 0 点
4. **用量可查**：`python monitor.py --stats`（今日请求数/退避状态/降速倍数）、
   `python monitor.py --plan`（按 schedule 估算用量并对照预算）

当前默认配置下的用量估算：4 个 sku 目标（1 分钟/3 分钟）+ 1 个搜索目标（10 分钟）
≈ 3340 次/天，预算 4000 约 20% 余量；高发时段单个商品的检测延迟 ≤60 秒。

### 5.2 判定与防误报

1. 主判定：`remindMessageTip` 为空 **且** sku `usableStocks > 0`
2. 二级确认：命中后立即用 `app_get_h5product_sku_check` 复核（这也是下单第一步，顺带做）
3. 防抖：状态机只对「缺货→有货」跳变告警；`monitor_state.json` 记录已告警 episode，重启不重复轰炸
4. 可选持续提醒：`realertMinutes > 0` 时有货期间每 N 分钟重复推送（适合你没看到手机的场景）
5. **每日限购**：每品种每天限量 1 张。`monitor_state.json` 的 `purchased` 字段记录
   `skuId -> 日期`；下单成功（或订单创建待支付）后该 sku 当天跳过监控/购买，日期变更自动恢复。
   手动买中后可执行 `python monitor.py --mark-purchased <skuId>` 立即生效（监控每轮重读状态文件，无需重启）；
   `--reset-purchased` 一键清除全部标记（测试用）。
6. **ID 自动校准**：商品频繁上架/下架，重新上架后可能分配新 skuId/productId。对
   `calibrate: true` 的目标，启动时、每 `calibrateIntervalHours`（默认 24h）、
   以及接口报错时，自动用 `searchKey` 搜索并按商品名（精确 > 正则 > 包含）匹配更新 ID；
   校准记录存 `monitor_state.json` 的 `calibrated` 字段（重启不丢），ID 变化时推送通知；
   搜不到时（下架中）保留原 ID 继续监控。今日已购标记随品种迁移到新 ID。
   自动下单目标按商品名匹配，不受 ID 变化影响。

### 5.3 延迟预估

- 轮询周期期望 ≈ 间隔的一半（平均 5s，抖动后 ~4~6s）
- 接口本身 ~100~300ms（服务器在国内，Linux 服务器直连更快）
- **端到端预计 5~8s 内收到推送**，对"补货后通常几分钟才被抢完"的场景足够

## 6. 提醒渠道

原型 `notify.py` 已实现以下渠道，任选/多选，全部并发发送、单路失败不影响其他路：

| 渠道 | 延迟 | 特点 | 适用 |
| --- | --- | --- | --- |
| **Bark**（iOS） | 秒级 | 免费、可开关键声音/强制提醒 | iPhone 用户首选 |
| **ggsuper 全能BARK** | 秒级 | 国产跨平台，**有鸿蒙版**、走厂商通道支持离线 | **华为/鸿蒙/荣耀机型首选** |
| Telegram Bot | 秒级 | 免费稳定、多平台 | 双平台用户首选 |
| PushPlus | 秒级 | 微信服务号推送，免费额度 | 微信重度用户 |
| Server酱 | 秒级 | 微信/企微推送 | 同上 |
| 钉钉/企微/飞书机器人 | 秒级 | 群机器人 webhook | 已有群 |
| 自定义 webhook | - | POST JSON，可接自己的服务 | 进阶 |

**推荐组合：Bark（iOS）或 ggsuper（华为鸿蒙）为主 + PushPlus 为备用**，双路冗余防单点挂掉。
提醒内容包含：商品名、skuId、库存数、售价、时间、直达链接；Bark 与 ggsuper 还会带上
「点击通知直接打开该商品页」的跳转链接。

## 7. 自动下单：可行性、流程与护栏

### 7.1 结论：可行，已走通全链路

利用已登录态，按 H5「立即购买」同款流程：

```text
1. app_get_h5product_sku_check   {skuId}                  # 权威库存（顺带做二级确认）
2. app_set_h5product_shopcart_add {skuId, quantity, commitFrom:1}   # 返回 shopCartId
3. app_get_h5member_ptcard_list   {}                       # 取点数卡 cardNo + deducteNum
4. app_get_h5order_preview        {shopCartIdList, zpCardIds:[{cardNo,deducteNum}],
                                   orderExtInfo:{leaveMessage:"充值手机号:xxx",
                                                 merchantExtInfo:{}, addressId:""}}
   → 返回 orderWxPayAmount（微信补付）与点数抵扣明细
5. app_get_h5order_commit         同上参数
   → wxPayAmount=0 时直接生成订单（orderPayNumber）；>0 则需微信支付（H5 无法自动完成）
```

对京东E卡（直充电子券 verifyType=3）：无需收货地址，**订单备注必须写京东账号充值手机号**（商品页明确要求"需在订单备注充值手机号，未备注的默认充值收件号码"）。

### 7.2 内置护栏（auto_order.py）

| 护栏 | 说明 |
| --- | --- |
| `dryRun=true` 默认 | 只走到预览，**不提交、不扣任何款项**；确认预览数字OK后再关 |
| `maxWxPayAmount` | 预览微信补付超过阈值即中止（防点数不够时误用微信现金） |
| `quantity` | 默认 1，防手滑买多 |
| `targets`（多品种） | **只购买列出的 sku**，每项可独立配 `rechargePhone`/`quantity`/`maxWxPayAmount`；避免 search 模式发现多个商品时全部误买 |
| `matchName` | 备选：按商品名正则匹配购买目标（与 targets 二选一） |
| 每日限购 | 每品种每天限量 1 张：下单成功当天自动停止该 sku 的监控/购买，次日恢复；手动买中可 `--mark-purchased` |
| sku_check 复核 | 提交前再验一次库存，避免"看到有货→提交时已被抢空"的无效请求 |
| 异常兜底 | 任一步失败只记日志并推送失败通知，不影响监控继续跑 |

**开关方式**：`config.json` 的 `autoOrder.enabled` / `dryRun`，或环境变量 `ZPMON_AUTO_ORDER` / `ZPMON_DRY_RUN`（优先级更高，便于临时切换），改后重启进程生效。
**结果通知**：下单成功（含订单号）/ 待微信支付 / 提交前被抢空 / 加购失败 / 异常均会推送；演练模式也推送预览数字供核对（`notifyDryRun` 可关）。

### 7.3 你必须事先验证的事（ dryRun 输出会告诉你）

1. 132 的标价中，点数抵扣多少、微信补付多少（决定要不要备现金）
2. 两张卡的 `deducteNum` 与余额是否够扣一单
3. 备注手机号写对（充错号基本不可挽回）

## 8. 限制、风险与合规注意事项

### 8.1 平台规则风险（最主要）

- 此类自动监控+自动下单**几乎肯定违反商城用户协议/活动规则**（通常禁止"使用外挂、机器人、脚本"）
- 可能后果：账号被限制登录、订单被取消、**福利卡余额被冻结或清零**——这是你最大的实际损失点
- 频率风险：轮询过猛（<5s）或异常 UA/无签名单机并发，可能触发 IP 限流或账号风控。本方案用固定 UA、随机抖动、低频轮询规避，但不能保证

### 8.2 资金与操作风险

- 自动下单是真实扣款：预览没看清就关 dryRun，可能多扣/误扣
- 并发竞争：补货时多人抢购，可能提交成功但库存被回冲、或支付超时订单关闭（影响福利卡释放时效）
- 京东E卡充值手机号填错 → 充值到他人京东账号，基本无法追回
- token 泄露 = 账号被盗用下单/提现，务必保密

### 8.3 合规与法律边界（中国法域）

- **个人自用监控**处于灰色地带，一般不构成违法，但违反用户协议的后果（封号）需自担
- 若用于**批量抢购加价转售（黄牛）**，可能触及《反不正当竞争法》第十二条及平台治理规则，风险性质升级——**本方案仅面向个人自用消费**
- 逆向行为限于"复刻公开客户端签名以调用公开接口"，未绕过任何身份认证/支付安全机制；请勿用于扫描、薅羊毛、攻击
- `apiToken` 属于个人信息（《个人信息保护法》），妥善保管、不要共享给他人或第三方服务
- 以上不构成法律意见，重大决策请咨询律师

### 8.4 方案自身的限制

- 只能监控**网页版/H5 暴露的库存字段**；若平台改为前端硬编码"补货中"（不从库存字段渲染），需改判 DOM——目前接口直接返回库存，无此问题
- 库存按 `cityCode` 展示，**务必用你账号常用城市**（北京 110100；改城市只影响可购性与展示价）
- 接口字段/签名算法随版本可能变化：升级后抓包对比 `methodName` 与签名串即可，`zp_api.py` 里改一处
- 服务器若在海外，延迟会上升到 300ms+，仍可用但抢购竞争力下降；建议国内服务器
